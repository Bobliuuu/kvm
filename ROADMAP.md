# KVM roadmap: what is needed before release

Release bar: **nothing ships until it is PERFECT**: every suite green on every target GPU, every README number regenerated by one script, B200 and multi-GPU measured (not "not run"), and the speed claims compared against the strongest baselines (PyTorch eager, torch.compile + CUDA graphs, Megatron-style fused kernels) on the same hardware.

Status as of 2026-11-07 (evening). Numbers come from committed results; branch names are real. "Not run" means no result exists, not that it passes.

Reference point ("flapping airplanes level"): their own results, quoted in our README, show per-op kernels beating their megakernel by 13-25% on a 56 us step, and Megatron + CUDA graphs beating their VM on a 162M GPT (43.1 s vs 48.1 s, B200). Within ~10-15% of the best baseline on B200-class hardware, plus the fused-run / co-optimization demos, is the target, not "beats everything".

## 1. Branches to land (in this order)

1. `perf/admission-v2` : merges `perf/admission-bottleneck` + `perf/completion-path`, auto-sizes the admission window. bf16s 291.8 -> 150.6 ms.
2. `perf/chunked-release` (on 1) : chunked descriptor release, edges first, add-indegree race handling. bf16s 135 ms, f32 258 ms. Gates passed: exec suite, float64 grads.
3. `perf/gemm-tiles` : only keep the `-DKVM_MMA_SPREAD=1` BK=32 variant (head NT 0.54 -> 0.67x) after gates.
4. `results/coopt-sh` : in-kernel retire/PBT benchmarks under `bench/coopt/`, self-contained, safe any time.
5. `integration/green` : the all-green integration branch (Phase A).
6. `feat/hopper-sm90` : rebase onto the merged result in Phase C.

## 2. Phases (do them in order; each phase has an exit gate)

### Phase A: green on A100 (sm_80), reproducible  [~1 week]
- [ ] **Standalone litmus-mutant suite hangs / prints nothing on admission-v2 and later** (built, no output in 2 h). Root-cause (deadlock in new admission path vs buffering) and fix.
- [ ] Re-run on the new executor: sanitizers, negative controls, model zoo, 300-step learning curve vs torch, Doom + serve demo (700/700 frames identical, 35 Hz).
- [ ] `kvm_run` demo path does not use auto-sized/chunked admission (only `kvm_exec` main does): wire it in.
- [ ] Zoo: 2 of 28 fail the weight check: `vit_bf16s` (key-projection bias has a mathematically zero gradient, AdamW amplifies noise: fix the check) and `san_bf16s` (2 steps, 1.7e-2 vs 1e-2 gate: confirm golden/tolerance vs kernel).
- [ ] `test_ops` T=1 attention-backward bound (`kT1Abs = 1e-4`): confirm on every shape, close the README item.
- [ ] `recycle` long-running admission flake (3M tasks / 4096 slots failed 2 of 3 runs): root-cause on the chunked admitter.
- [ ] Merged executor ~6% slower than pre-merge (additive: +1.8% attn, +4.4% bf16): accept or tune.
- [ ] `scripts/run_all_green.sh` (Modal entry) printing ONE PASS/FAIL table; regenerate every README badge and number from it.
- **Exit gate:** table is all PASS on A100, run twice from a clean checkout, results committed.

### Phase B: A100 performance  [~1-2 weeks, can overlap with C prep]
Profile (chunked, bf16s): utilisation ~71%, queue wait p50 55 us / **p99 3.2 ms**, matmul 43% of task time at 0.5-0.7x cuBLAS, per-hop ~7 us.
- [ ] One batched executor rebuild (builds are ~40 min): persistent-tile chaining; critical-path priority (longest-remaining-path rank in `compile_workload`); per-SM-group local ready queues with stealing; cheaper completion path. Target per-hop 7 -> <3 us, p99 queue wait < 500 us.
- [ ] GEMM tiles to >=0.9x cuBLAS: split-K / stream-K for skinny wgrad (check grid fill and wave quantization on 108 SMs first), warp-specialized producer/consumer with mbarriers, per-shape tile selection at compile time (128x256 / 256x128 / 64x256), fused epilogues.
- [ ] Reduce task count by fusion into GEMM epilogues (`--fuse` currently changes nothing: 58,634 tasks); larger elementwise/norm/optimizer tiles were measured and are slower, so do NOT coarsen.
- [ ] Attention fwd/bwd tiles (flash-style online softmax, bf16 mma): currently 15-30% below torch SDPA.
- **Exit gate:** 162M GPT bf16s within 1.3x of torch eager on A100 (stretch: within 1.5x of the CUDA graph), same-container interleaved measurement, torch re-measured in that container.

### Phase C: Hopper and Blackwell (H100/H200 sm_90, **B200 sm_100**)  [~2-3 weeks]
Required before release: the reference result is on B200, so we must measure on B200 and not extrapolate from A100.
- [ ] Rebase `feat/hopper-sm90` onto the Phase-A/B result; build for sm_90a. Port tiles to **wgmma + TMA + mbarrier pipelines**, clusters/DSMEM where it helps; keep the sm_80 path working (arch dispatch, one binary per arch).
- [ ] Blackwell sm_100: **tcgen05 / TMEM-based GEMM**, TMA multicast, 2-CTA MMA; bf16 and fp8 paths. Needs a recent CUDA 12.8+ toolkit.
- [ ] Re-run the FULL green table (Phase A) on **H100, H200 and B200**: executor suite, litmus + mutants, sanitizers, zoo, grads vs float64, Doom + serve demo, learning curve. Memory-model assumptions differ per arch: re-audit every fence and ordering in the litmus suite on each arch.
- [ ] Baselines on the same boxes: PyTorch eager, torch.compile, torch CUDA graph, and a Megatron-style fused-kernel run for the 162M GPT (reproduce the reference 43.1 s vs 48.1 s comparison on B200 ourselves and put ours next to it).
- [ ] How to get the hardware (no Vast): Modal (H100, H200, B200 GPU types; watch the 10-GPU workspace cap and queue times), AWS p5 (H100) / p5e / p6-b200 (B200) in a region with quota (the lab account's P quota is 128 vCPU in us-east-1 only; request increases in the Service Quotas console, the IAM user cannot file them via API). Budget a day of B200 time per full green run; get a quota/credit plan BEFORE starting this phase.
- **Exit gate:** green table on A100, H100 and B200; speed table vs all baselines on each; no "not run" cells.

### Phase D: multi-GPU  [~2-3 weeks, partly parallel with C]
Currently "not run". A persistent per-GPU VM needs a story for cross-GPU dependencies.
- [ ] Design (`DISTRIBUTED.md`): one VM per GPU; dependency edges that cross GPUs through NVLink/NVSwitch peer memory (P2P remote counters/queues via NVSHMEM-style symmetric allocation or CUDA IPC mem handles), NCCL-free collectives implemented as tasks (all-reduce / reduce-scatter / all-gather as task graphs), overlap of gradient comm with backward as ordinary dependency edges.
- [ ] Implement: remote-edge protocol (indegree decrement over peer memory with the right fences/ordering), collective tasks, data-parallel first (all-reduce grads), then tensor-parallel for the big GEMMs, then pipeline stages.
- [ ] Correctness: litmus tests for the cross-GPU edge protocol (the same mutant methodology: inject ordering bugs, confirm detection); grads on 2/4/8 GPUs equal the 1-GPU run within tolerance; learning curve match.
- [ ] Measure on **2, 4 and 8 GPUs** (NVLink boxes: 8xA100/H100/H200/B200 nodes via Modal multi-GPU functions or AWS p4d/p5/p6): scaling efficiency vs PyTorch DDP and FSDP/Megatron on the same GPT; also the PCIe-only case as a negative control.
- **Exit gate:** 2/4/8-GPU green table, scaling table vs DDP/Megatron, honest "where it loses" section.

### Phase E: co-optimization use cases  [~1-2 weeks, after B]
Done: `bench/coopt/` trains a population in ONE kernel with in-kernel retire rules and PBT (held-out eval inside the VM). 1.4-2.0x vs torch + CUDA graphs on small models, 0.59-0.9x on 128/256 where cuBLAS wins.
- [ ] Ping-pong buffers so the optimizer overlaps the next forward (single-buffered overlap was slower).
- [ ] Adam/momentum state in PBT copies; a real 10-50M GPT instead of a 2-layer MLP once GEMMs are fast.
- [ ] Whole-training-run in one launch; in-kernel data pipeline/RNG; train + serve co-location at scale.
- [ ] Repeat the headline co-opt results on H100 and B200 (and on multi-GPU: population across GPUs).

### Phase F: release candidate  [~1 week]
All of this must be true, with links to committed results, before any tag or public announcement:
- [ ] `scripts/run_all_green.sh` is all PASS on A100, H100, H200 and B200, plus the multi-GPU rows, from a clean clone, run twice.
- [ ] The README's every number, badge and chart is generated from those results by a script (no hand-typed numbers); "Honest limits" updated to match what was measured; no "not run" cells left except ones explicitly out of scope with a reason.
- [ ] Baseline fairness section: torch eager, compile, CUDA graphs, Megatron/DDP configured by us with tuning notes and the exact versions, same hardware per row.
- [ ] Independent review: a fresh agent/person reproduces the headline numbers from the README commands alone on a clean machine.
- [ ] Security/hygiene pass: scan_leaks on full history (clean), no hosts/IPs/keys, licence, citations to the original kittens VM work (not affiliated).
- [ ] Cost and runtime documented (how long the full green run takes, how much it costs).
- [ ] Only then: tag, release notes, public post. Anything that fails a gate delays the release; do not ship with a known red.

## 4. Practical notes for whoever picks this up

- Each `kvm_exec` nvcc build takes ~40 min: cache binaries on a Modal volume, one `-arch` per build, batch changes per build.
- Modal has a 10-GPU workspace cap; queues were hours long when many agents ran. Run few jobs at a time and use `modal run --detach` or a deployed app (a backgrounded local client that dies can kill the run). Stop ephemeral apps when done; check `modal app list` first.
- Compare variants interleaved inside ONE container; GPU SKUs differ between Modal containers (A100-40GB SXM vs 80GB PCIe changed baselines by ~10%), and cuBLAS varies 124-161 TFLOP/s run to run in shared containers. Re-measure torch in the same container.
- No Vast. Hardware is Modal or owned AWS; confirm cost before launching expensive boxes (B200 and 8-GPU nodes are many dollars per hour).
- Repo history was rewritten on 2026-11-07 to remove a leaked address. Local clones need `git fetch && git reset origin/<branch>` (mixed reset keeps the working tree); the pre-push hook blocks pushing old history.
- No IPs, hosts or keys in committed files; ssh only through `~/.ssh/config` aliases; run `scan_leaks.sh` before commit/push.
